# Проверки 2026-10-02

Изменения проверены локально на Windows, RTX 3070 Ti (8 GB), Python 3.12. Финальная поставка использует официальный `llama-cpp-python 0.3.36/cu124`. Qwen3.5 4B Q4_K_M (2.52 GiB) из LM Studio проверена в трёх режимах. Qwen и TinyLlama включены в portable-папку с относительными путями; папка переносится целиком.

## Runtime и API

27 регрессионных тестов проходят: независимое чтение stderr, повторное использование worker, общий и idle timeout, остановка незавершённого потока, crash/EOF, завершение дочерних процессов Windows, освобождение блокировки после ошибки, 409 при занятом inference, изоляция истории, memory on/off, обрезка завершённых пар, oversized prompt, повреждённый JSON, атомарная запись, API key/disabled API, OpenAI SSE и отключение клиента. Дополнительно проверены неизменность createdAt и старые временные метки, сохранение названия/даты диалога при обновлении ответа, перенос packaged-путей, сохранение числа GPU-слоёв после ротации stderr, отключение KV/operation offload в CPU-режиме и завершённый think-блок без открывающего тега в completion.

Команда: `backend/.venv/Scripts/python.exe -m unittest discover -s tests -v`.

До обновления CUDA runtime с 0.3.4 до 0.3.36 в реальном EXE на TinyLlama выполнены семь smoke-проверок (`tools/smoke_runtime.py`, результаты `tools/out/exe_live_results.json`):

- CUDA отвечает; два запроса используют один PID worker. Первый ответ 1.188 s, повторный 0.047 s. Это единичные замеры короткого запроса, не сравнительный benchmark.
- Продолжение двухходового диалога возвращает кодовое слово ORBIT; memory=false выполняет отдельный запрос.
- Занятый runtime возвращает 409, health отвечает за 0.016 s; отмена и последующий запрос восстанавливают worker.
- Отключение HTTP/SSE клиента освобождает worker.
- Реальный timeout 1 s останавливает генерацию за 1.016 s; следующий запрос работает.
- CPU inference работает; после него CUDA восстанавливается.
- Канонический desktop API EXE/мини-помощника сохраняет и использует двухходовую историю.

В браузере проверены отдельные диалоги, память, поток ответа и общий desktop store. Frontend TypeScript/Vite собирается. Portable health check завершён без ошибок. После установки иконки EXE пересобран; наличие ICO/PNG в поставке и PE-ресурса EXE проверено, история до/после пересборки сохранена.

В EXE с TinyLlama runtime сообщал `gpu_offloaded_layers=23`, `model_layers=23`, `mode=CUDA`, fallback отсутствовал. NVIDIA также показывала embedded inference worker среди GPU-процессов. Это фактические 23/23 слоя TinyLlama на GPU.

## Три режима на Qwen3.5 4B

В EXE с 0.3.36 выполнен `tools/check_inference_modes.py --model-name "Qwen3.5 4B" --model-path "dist/models_storage/Qwen3.5_4B/Qwen3.5-4B-Q4_K_M.gguf" --mixed-layers 16`. Результаты: `tools/out/qwen35_4b_three_modes.json`.

| Режим | Запрошено GPU layers | Фактически на GPU | Завершённый ответ | Время с загрузкой |
|---|---:|---:|---|---:|
| CPU | 0 | 0/33 | Four. | 69.000 s |
| CPU + CUDA | 16 | 16/33 | Four. | 28.172 s |
| CUDA | -1 | 33/33 | Four. | 13.875 s |

Во всех случаях `finish_reason=stop`, fallback отсутствует. Контекст 1024, batch 64, flash attention включён. В CPU-режиме KV и operation offload отключены. Служебные операции приложения выполняются CPU даже при размещении всех слоёв модели на GPU.

Это проверки работоспособности, не benchmark скорости: CPU сгенерировал 346 токенов, два GPU-режима — по 185. Первоначальный лимит 256 обрезал рассуждение на CPU; финальная проверка использовала лимит 512 и требовала завершённый ответ.

После финальной пересборки обычный `/api/chat` без стриминга на CPU завершился за 79.266 s при `worker_idle_timeout_sec=3`: heartbeat worker предотвращает ложный idle timeout во время расчёта, а общий request timeout остаётся ограниченным. Итог `Four.` отделён от 1304 символов рассуждения. Результат: `tools/out/final_nonstream_cpu.json`.

Финальный веб-чат с Qwen3.5 4B отвечает `4` на первый вопрос и вспоминает прежний вопрос `Сколько будет 2 + 2?` на следующем ходе. Показаны исходные даты 21:49 и 21:53; имя `Qwen3.5 4B · CUDA` сохраняется после ответа. Runtime подтверждает 33/33 слоя на GPU. Предыдущие диалоги сохранены.

Дополнительные изменения: даты сообщений, разнесение реплик слева/справа, ручная прокрутка без сброса и скрываемый список диалогов мини-помощника. Наличие реального Tk Listbox и обоих диалогов проверено через диагностику запущенного EXE. `tools/check_native_dialogs.py` проверяет настоящие Tk-контролы с отдельной временной историей: создание диалога, выбор прежнего, сохранение текста/времени, скрытие панели и сохранение позиции чтения. Пользовательские файлы не затрагиваются. Визуальная проверка native Windows GUI через автоматизацию в текущей сессии недоступна.

В браузере выполнен запрос при ручной прокрутке к началу: после ответа scrollTop остался 0, а высота истории выросла с 803 до 1029 px. Новые сообщения показывают `02.10.2026, 20:59`; ISO createdAt сохраняется в desktop store. Проверены разнесённые реплики пользователя справа и модели слева.

## VetConsult

Проверен настоящий клиент `app.services.llm.llm_client.openai_compat_complete` из работающего репозитория VetConsult: ответ `Two plus two is 4.`.

После обновления runtime повторно проверен этот же штатный клиент с Qwen3.5 4B через `/v1/chat/completions`: завершённый ответ `Four.` после think-блока, 33/33 слоя на GPU без fallback. Результат: `tools/out/vetconsult_qwen4b_client_result.json`. OpenAI-compatible content этой модели содержит её think-блок; native чат показывает рассуждение отдельно. Сохранённое подключение VetConsult по-прежнему указывает на TinyLlama.

Через обычную администраторскую cookie-сессию в браузере сохранено подключение `local-ai-gpp`, revision 1, provider `openai_compat`, base URL `http://127.0.0.1:8765/v1`. POST `/llm/test` с сохранённым connection_id возвращает:

```json
{"ok":true,"mode":"connection","connection_id":"local-ai-gpp","provider":"openai_compat","answer":"Two plus two is 4."}
```

Рабочие профили и активное подключение VetConsult не переключались. Обычный мастер «Модели» этой сборки предлагает только OpenRouter, DeepSeek, Hugging Face и локальные файлы. Поэтому использован пример `examples/vetconsult_connector.html`, временно размещённый на текущем origin VetConsult с явного разрешения пользователя. ## Адаптер Qwen

В метаданных проверочной модели `general.architecture=qwen35`, GGUF-шаблон содержит штатную ветку `enable_thinking=false`. Адаптер использует её по умолчанию, а не фильтрует готовые токены. Другие модели сохраняют исходный формат; адаптер не принуждает старые Qwen-шаблоны без этого параметра к несуществующему режиму.

На Windows EXE с CUDA `/api/chat` вернул `Four`, пустое reasoning, `finish_reason=stop`, один выходной токен. Через `/v1/chat/completions` отдельно включён и выключен флаг: при true — 253 выходных токена и завершённый think-блок, при false — один токен без think-блока. PID worker одинаковый в обоих запросах: веса не перегружены. Единичные запросы подтверждают управление режимом, не качество модели или универсальное ускорение.

После финальной сборки повторена проверка всех трёх режимов с адаптером и выключенными рассуждениями:

| Режим | GPU-слои | Ответ | Токены ответа | Время с загрузкой |
|---|---:|---|---:|---:|
| CPU | 0/33 | 4 | 1 | 2.422s |
| CPU + CUDA | 16/33 | 4 | 1 | 2.360s |
| CUDA | 33/33 | 4 | 1 | 2.344s |

Везде `finish_reason=stop`, `enable_thinking=false`, reasoning пустое, fallback отсутствует. Ранее приведённая таблица 69/28/14s относится к проверке до адаптера, с рассуждениями. Сравнение разных запросов и холодной/тёплой файловой памяти не является benchmark.

## Linux Docker

Собраны оба образа и запущены health-checked контейнеры Linux/amd64 на Docker Desktop. Проверены React page, JS/CSS, `/api/health`, bootstrap, `/v1/models`, OpenAPI, Swagger и proxy branding. GGUF из LM Studio подключён read-only через `/models`, настройки и логи сохраняются в `/data`.

`tools/check_docker.py` с настоящей Qwen3.5 4B Q4_K_M вернул `Four`, `finish_reason=stop`, CPU, адаптер qwen, `enable_thinking=false`, reasoning пустое. Холодный запрос занял 83.25s с загрузкой через Windows bind mount; это не benchmark нативной Linux-системы. Пример `examples/client.py` проверен через Nginx: первый ответ `OK`, второй SSE-ответ `ORBIT`, история содержит четыре сообщения, терминатор [DONE] получен.

При первой проверке обнаружена потеря heartbeat: quiet-режим llama-cpp-python перенаправлял stdout и stderr в /dev/null во время загрузки GGUF. Worker теперь сохраняет нативную диагностику, а родитель отдельно читает ограниченный stderr. Повторная реальная загрузка/inference завершилась. Общий request timeout остаётся ограниченным.

Внутри собранного Linux-образа проходят 26 тестов; один Windows Job Object тест пропускается по платформе. На Windows проходят все 27. Workflow проверяет обе платформы и сборку/запуск Docker с web/API без скачивания GGUF. Текущее состояние конкретного Git-коммита видно в [GitHub Actions](https://github.com/wladsergeew013-glitch/local_ai_gpp/actions/workflows/ci.yml).

## Linux CUDA Docker · 2026-10-03

Собран `backend/Dockerfile.cuda` и запущен Compose с `docker-compose.gpu.yml` на Docker Desktop/WSL2. Контейнер Linux/amd64 видит RTX 3070 Ti 8GB, драйвер хоста 616.92. Runtime: CUDA 12.4.1, Python 3.10.12, официальный `llama-cpp-python 0.3.36/cu124`; SHA-256 wheel совпал с GitHub release. GGUF подключён read-only; проверка использовала отдельный project и порты.

На одной Qwen3.5 4B Q4_K_M проверены три режима, контекст 1024, batch 64, fallback запрещён:

| Режим | Запрошено GPU-слоёв | Фактически на GPU | Ответ | Время с загрузкой |
|---|---|---|---|---|
| CPU | 0 | 0/33 | Four | 102.454s |
| CPU + CUDA | 16 | 16/33 | Four | 142.469s |
| CUDA | -1 | 33/33 | Four | 89.156s |

Во всех случаях `finish_reason=stop`, один токен ответа, `enable_thinking=false`, reasoning пустое, fallback отсутствует. Это проверки работоспособности: холодные загрузки через Windows bind mount и инициализация runtime входят во время, поэтому числа не сравнивают скорость вычисления токенов и не являются benchmark нативного Linux SSD.

Python-клиент через Nginx на CUDA вернул `OK`, затем `ORBIT` в SSE; история содержит четыре сообщения, `[DONE]` проверен. Оба запроса использовали уже загруженный worker с 33/33 слоями на GPU и заняли вместе 0.468s. Это единичный smoke-тест памяти/streaming. `nvidia-smi` внутри контейнера также подтверждает GPU; после проверки на устройстве было занято 4585 MiB (общая память устройства, не изолированный расход worker).

CI отдельно собирает CUDA-образ, запускает 26 регрессий с одним Windows-only skip и проверяет API на runner без GPU. Реальный GPU inference подтверждён локально в Linux-контейнере. Установка драйвера и NVIDIA Container Toolkit на отдельном физическом Linux-хосте, другие GPU/модели и качество ответов не проверены.
